# The shared Motorola 68000 (side track P)

Plan and gates: PLAN.md, "Side track P". Log: docs/status/side-p.md.

## The user's decisions (2026-10-18)

- **The MC68000** first; a 68010 may follow (VBR, loop mode, the bus
  error frame), so nothing here assumes there's only one.
- **Bus-cycle exact.** The model and the core make the same bus accesses,
  in the same order, with the same cycles as the chip.
- **For another project of the user's** that benchmarks a CPU design
  against a 68000 simulation: the Haskell model as a library (`M68k.Run`,
  P.3), the Clash core in Verilator with a Zig harness, and the same as a
  C ABI library (P.5).
- **First system:** the Amiga 500 or the Atari ST, chosen at P.6.

## The tests

Tom Harte's 680x0 SingleStepTests (MIT; github.com/SingleStepTests/680x0
at commit e0d5ece; `tools/fetch-roms.sh`, `roms/m68k/v1/`): 124 files (and a README), one
per instruction and size (`ADD.b`, `MOVE.q` = MOVEQ, `Bcc`, ...), 8065
cases each, 1,000,060 in all, gzipped JSON, read through the Haskell
`zlib` package. A case:

- `initial`, `final`: d0-d7, a0-a6, usp, ssp, sr, pc, `prefetch` (two
  words: IR, the opcode being run, at `pc`, and IRC, the word after it),
  `ram` (address, byte pairs: every byte the instruction touches).
- `length`: its cycles.
- `transactions`, in order: `["n", cycles]` (idle), and `[kind, cycles,
  fc, address, size, data]` for kind `r` (read), `w` (write), `t` (TAS's
  read-modify-write cycle); size `.b` or `.w`; function codes 2 (user
  program), 5 (supervisor data), 6 (supervisor program) in these files.

Seen in NOP's first case: pc 0xC00, prefetch `[0x4E71, IRC]`; NOP reads
the word at pc + 4 (one 4-cycle read) and ends with pc 0xC02, prefetch
`[IRC, the word read]`. So the model's `pc` is the address of the
instruction in IR, and the queue runs two words ahead, as the chip's does.

**Where the set is doubtful** (each a named rule or list, easy to change):

- **Corrupt cases**, skipped by name (`knownBad` in `test/Spec.hs`): ASL.b
  #2,D2 cases 1583 and 1761 expect D2's upper 24 bits to change, which a
  byte shift can't do.
- **ASR past the operand's width** (a register count above 8, 16 or 32):
  the set clears C and X even for a negative value, where a bit-by-bit
  shift would leave them set (the sign shifted out; Musashi and MAME set
  them). The model follows the set (`past` in `shiftOp`); open for a
  check on a real 68000.
- **DIVS's overflow timing:** the set takes the short path (16 cycles
  plus the operand's) for a signed overflow too, where Jorge Cwik's
  analysis has it only for an absolute one. The model follows the set
  (`divsCycles`).
- **Divide by zero** is nearly untested: one case in 16,130, whose frame
  holds the DIVU's own address where the manual (and MAME) push the next
  instruction's. The model keeps the manual's PC and that case's flags
  (N, Z, V, C cleared), and skips the case (`knownBad`); its own tests
  come with P.2's last part.

All 124 files pass whole, 1,000,057 cases (2026-10-18, `EMU_FULL_TESTS=1
cabal test m68k-spec`, 77 s).

Not in these tests: interrupts, the bus error, RESET's and STOP's
timing beyond one instruction, HALT, DTACK wait states. Those get their
own tests (P.2's last part).

## The model (`cpus/m68k/src/M68k/Spec.hs`)

Pure Haskell, spec first (CLAUDE.md rule 1). Its state: the registers,
SR, the two-word prefetch queue (IR, IRC), and whether it is stopped or
halted. One instruction is `step :: Bus m => Cpu -> m Cpu`, written
against a small bus class:

- `busRead fc size address`, `busWrite fc size address word`, `busTas`
  (the indivisible read-modify-write), each a four-cycle bus cycle;
- `idle cycles` (internal cycles, two at a time).

The tests run `step` in a monad that serves the case's RAM and records
every access with its cycles, then compare the list with `transactions`.
The library (P.3) runs it over a memory image in ST or IO. The address
bus is 24 bits (A1-A23 with UDS/LDS): addresses on the bus are masked to
24 bits; a word access at an odd address is an address error before any
bus cycle (group 0 exception, its 14-byte frame).

Per-instruction bus sequences follow Jorge Cwik's "Yet Another Cycle
Hunting Table" (YACHT, 2008, public: the order of `np` prefetches, `nr`
reads, `nw` writes and `n` idles for every instruction and addressing
mode, from Motorola's microcode), checked case by case against the tests.
Cycle counts of MULU, MULS, DIVU and DIVS depend on the data, as the
tests record them.

## The library and the runner (P.3, for the benchmark project)

`M68k.Run` (the `m68k` package's library): a `Machine` with 16 MiB of
memory (the 24-bit bus, no devices), `loadImage`, `resetCpu` (SSP and PC
from the vectors at 0) or `startAt pc ssp`, `stepOne`, and `run m
(Cycles n | Instructions n)`, which ends at STOP, a fault the model can't
go on from, or the limit, with `Stats` (cycles, instructions, why it
stopped). `setTrace` hands every instruction (address, opcode) and every
bus cycle (read, write, TAS, idle, with function code, size, address,
data) to a callback, in order. Cycles are the model's: four per read or
write, ten per TAS, the internal cycles as the chip spends them, no wait
states; the reset sequence isn't counted.

`m68k-run IMAGE [--at ADDR] [--pc ADDR [--sp ADDR]] [--cycles N |
--instructions N] [--trace]` (`cabal run m68k-run -- ...`): the same from
the command line, printing the counts, why it stopped and the registers.
Speed: about 1.3 million instructions (13 million cycles) a second on
the worker, about 1.6 times an 8 MHz 68000.

Programs: GNU as for m68k is in the dev shell (`m68k-unknown-linux-gnu-as
-m68000`, then `m68k-unknown-linux-gnu-objcopy -O binary` for a raw image;
Motorola mnemonics with `%` register names, `|` comments). `make m68k-asm`
assembles every `cpus/m68k/test/asm/*.s` into `build/m68k/asm/*.bin`, e.g.

> nix develop -c make m68k-asm
> cabal run m68k-run -- build/m68k/asm/sum.bin --at 0x1000 --pc 0x1000 --sp 0x8000

Golden (`m68k-lib`): a hand-assembled loop summing 99 down to 0 with DBRA,
then STOP: D0 = 4950, 203 instructions, 1820 cycles. Not in the
SingleStepTests, so from the manual and YACHT and untested against a chip:
STOP (its own timing), ILLEGAL and lines A and F (as the privilege
violation), DBcc's expired counter (14 cycles, the branch target's word
fetched and thrown away first: that read's address is unverified).

## Interrupts and trace (P.2's last part; not in the SingleStepTests)

The bus gives the interrupt level (`busIpl`, IPL2-IPL0, sampled before
each instruction) and answers the acknowledge cycle (`busIack level`: a
vector number, or Nothing for an autovector, 24 + level). A level above
SR's mask is taken instead of the next instruction; level 7 whatever the
mask, on its rising edge only (`cIplSeen`). The sequence, 44 clocks
(YACHT): 6 idle, the PC's low word pushed, the acknowledge cycle (4
clocks, function code 7), 4 idle, SR and the PC's high word pushed, the
vector, the queue filled; SR then has S set, T cleared, the mask at the
level; a STOP ends (the PC pushed is the one after it). With SR's T bit
set at an instruction's start it is followed by the trace exception
(vector 9, 34 clocks, the next instruction's PC in the frame). In the
library: `setIpl m level`, `setIack m (\level -> ...)`; a run ends at STOP
until an interrupt comes, and interrupts don't count as instructions.
Tests: `m68k-lib` (levels and the mask, a device's vector, level 7's
edge, STOP woken, trace). **The bus error:** the bus says after each
cycle whether BERR ended it (`busBerr`); the model then runs group 0 as
for the address error, vector 2, the same 14-byte frame and timing
(untested against a chip). In the library `setBerr m (\addr -> ...)` names
the addresses where no device answers (an Atari ST's TOS finds its
hardware this way); `m68k-lib` checks a probe's frame. Not modelled yet:
the autovector's E-clock synchronisation (VPA: up to 10 more clocks on the
chip), the trace of an instruction that itself takes an exception, HALT
after a double fault (the model stops with a fault).

## The core (P.4, `cpus/m68k/src/M68k/Core.hs`)

The model's bus transactions as a state machine, one transition per
transaction (as the Z80's, `cpus/z80/src/Z80/Core.hs`), written again
independently of the model:

- **The request** (`cReq`, a register): a read or a write (a byte or a
  word, four clocks), TAS (ten), n idle clocks, or the interrupt
  acknowledge, with its function code and address: exactly the calls the
  model makes on its bus, in the same order. `cpuStep` gets the data when
  it's over (with BERR, the interrupt level, VPA) and returns the state
  with the next request; nothing in a request depends on its own data
  (TAS's write is the clock wrapper's: bit 7 set on what it read).
- **State changes in the model's order:** one the model makes before an
  access, when the access is issued; one after, when it's over. An odd
  word address is found when the access would be issued (the address
  error, no bus cycle); BERR when it's over (its results not applied). So
  a group 0 frame holds what the model's does.
- **The sequencer:** an instruction is a chain of steps; the shared ones
  (an operand found and read, a result written, an extension word, the
  prefetch) take a continuation, called at once when no transaction is
  needed (a register operand) or through a tag (`cRet`) when the
  transaction is over. Steps only issue requests or call later steps: no
  recursion, which Clash needs.
- **A7** is the active stack pointer, the other in `cOsp`; a change of
  SR's S bit swaps them.
- **Instruction boundaries:** `cpuFinish` stops at `PBound` when an
  instruction is over, before the next starts (its first steps can change
  registers before its first transaction); `cpuStep` is `cpuFinish` and
  the start of the next, in one transition. The lockstep tests compare the
  state at `PBound`.
- **The clock wrapper** (`M68kT`, `m68kTick`): counts the request's
  clocks, ends it on its last one, a bus cycle only with DTACK (or BERR,
  or VPA on the acknowledge): without it, a wait state at a time.

**`m68k-lockstep`** (`test/Lockstep.hs`, `test/M68k/CoreRun.hs`): the core
over the SingleStepTests, its requests made through the model's bus
(`M68k.SingleStep.runCaseWith`), compared as the model is. **`make
m68k-hdl`**: Clash on `cpus/m68k/hdl/M68kTop.hs` (the clock wrapper with
the bus as ports), Verilator's lint.

Stages (each gated by its files passing whole in `m68k-lockstep`, full

the structure isn't hardware's: each of the step function's ~70 phases
returns a whole new state record (about 1,100 bits), so Clash builds
full-record multiplexers at every decision, nested; besides that the
dividers are combinational (four 34-bit, DIVU's 15-step clock count),
the shifts 64-bit barrels, and dozens of register reads each an 8-to-1
mux of 32 bits. Cores of the chip in FPGAs take about 5,000 LUTs.

7. **P.4g, the hardware's structure** (from 2026-10-21; the design

   it runs every test. Gate: m68k-lockstep whole, full tier (the
   SingleStepTests and the random programs) on Core2; `make m68k-sim-test`
   on it; it fits the XC7Z020 beside a machine (budget: under 10,000
   LUTs, `make m68k-ooc`); its Fmax (an 8 MHz 68000 needs 8 MHz: a
   transaction is four clocks).

### P.4g's first result (2026-10-21)

`M68k.Core2` runs every SingleStepTests file whole (`m68k-lockstep2`,
full tier: 124 files, 1,000,057 cases), lint clean. **Its size**
(`make m68k-ooc M68K_TOP=M68kTop2`, routed): 51,505 LUTs (97% of the
XC7Z020; Core: 116,509), 1,097 registers, 1,657 CARRY4 (Core: 5,092), 3
DSPs; the worst path about 450 ns at a 20 ns clock (-429 ns slack):
**about 2 MHz**, where an 8 MHz 68000 needs 8. Clash: 14 minutes, 1.07 M
lines of Verilog.

The datapath's sharing worked (the adders a third of Core's; the
datapath about 10,000 LUTs by its parts). **The control is the rest**:
its command is built by long chains of record updates (the transaction's
end, the continuation, the next instruction's decode and start, the
operand's steps) in one step, so synthesis keeps wide nested
multiplexers several hundred levels deep instead of decode logic. The
chip's answer is microcode: the sequencer's state an address into a ROM
of microinstructions (a block RAM), the opcode only at dispatch points
and in the datapath's field substitution (register numbers, sizes, the
ALU's operation).

**After the shifter's fix** (f191ddd: its count's modulo had been two
64-bit `Int` dividers, the 1,227-CARRY4 path): 43,798 LUTs, 302 CARRY4,
the worst path 132 ns (187 levels, 60 CARRY4): **about 7.6 MHz**. The
area is now the multiplexers (the control's, and the datapath's wide
source selectors: about 6,000 LUTs by their parts): microcode for the
first, narrower selectors for the second. **Measured** (`M68kTopDp`: the
datapath alone, its command shifted in from a pin): the datapath 14,577
LUTs, its worst path 106 ns (about 9.4 MHz: the divider's 16 steps);
so the control about 29,000. Both shrink: the control by microcode, the
datapath by narrower source selectors (each one only the sources its
users need) and, if the budget needs it, a divider that iterates in
DIVU's own idle clocks.

**The user's decision (2026-10-21): microcode our own core** (not a
third-party core, not simulation only).

### P.4h: the microcoded control (`M68k.Core3`)

Core2's datapath stays; its control becomes a microsequencer:

- **The control store**: a ROM of microinstructions (a few hundred
  words), one a transaction: what to do with the data just read, the
  datapath's command, the next request, the next microaddress. A word is
  symbolic where the opcode matters: a register is "bits 9-11's D", "bits
  0-2's A", A7, MOVEM's next; a size is the opcode's (normal or MOVE's)
  or fixed; the ALU's operation the line's, the immediate's, the quick
  form's or fixed; a constant the opcode's (MOVEQ's, ADDQ's, a TRAP's
  vector) or the word's own. A decoder substitutes the opcode's fields
  (small logic), then Core2's datapath runs the command.
- **Sequencing**: the next microaddress is the next word, a jump, a call
  (the return address kept in a register: the operand routines'), a
  return, a dispatch (a table indexed by an addressing mode, or the next
  instruction's entry: a decoder of IR, where Core2's long @exec@ chain
  was), or the instruction's end (the trace exception, an interrupt, STOP,
  or the next instruction's entry).
- **Conditions within a step**: a word may name a condition (a condition
  code, DBcc's counter at 0, CHK's comparisons, a zero divisor, MOVEM's
  end, supervisor mode); when it holds, the word after it runs instead
  (the store read two words at a time), so a step's own actions can
  depend on a condition without a deep logic chain.
- **Faults**: BERR replaces the step with group 0's entry; the address
  error stays the datapath's override.
- The microcode is a Haskell DSL (`M68k.Microcode`: labels, words built
  with the steps' vocabulary), assembled at compile time into the ROM's
  contents and the dispatch tables.

Gates as P.4g's (every test whole; `make m68k-sim-test`; under 10,000
LUTs, 8 MHz or more), and in stages as P.4a-f were.

**First result (2026-10-21):** `m68k-lockstep3` whole, full tier: all 124

**Then** (2026-10-21/22): each datapath field's source among its own few

### P.4g's design: control and datapath

The transaction stays the unit (one transition each, the same requests),
but a transition is two functions:

- **Control** (`control`): from the sequencer's state (the phase, step,
  continuation tag, opcode, operand size and kind: tens of bits), the
  small registers it may look at (IR, IRC, the extension word, SR), a few
  condition bits (below) and BERR, a **command**: narrow fields, most of
  them selectors. Written as now (the same steps and continuations), but
  each step sets command fields instead of computing values: a value is a
  *source* (`Src`: the data just read, a temporary, a register file port,
  the ALU's or the address unit's result, the PC, a constant), and the
  temporaries are tracked symbolically within the step (a temporary
  written and read in one step is read as its new source).
- **Datapath** (`datapath`): applies the command with one of each unit:
  - the register file, 16 x 32 (D0-D7, A0-A7, A7 the active stack
    pointer; the other in its own register), **fixed read ports** whose
    addresses come from the opcode in use and the sequencer's state only,
    never from a condition (so no combinational loop through control):
    D and A of bits 9-11, D and A of bits 0-2, and one more (an index
    register from the extension word or IRC, A7, or MOVEM's next list
    register); two write ports with byte lanes (a byte or word written
    into Dn without reading it);
  - one ALU (add, subtract, logic, the X forms, compare, the shifts and
    rotates in closed form, BCD, bit operations, the flag rules of each),
    one 16 x 16 multiplier (a DSP), one 32 / 16 divider (unsigned, the
    signs outside; its quotient steps give DIVU's and DIVS's clock counts
    too);
  - an address unit (a base, a displacement or a step, an index) and a
    second small adder (MOVEM's -(An), a frame's addresses), the PC's own
    (+2, +4, a target less 4);
  - SR (the ALU's flags, a value with the stack pointers swapped on an S
    change, an exception's or interrupt's entry), PC, IR, IRC, the
    temporaries (operand address, value, source, two scratch, the
    extension word), the request (kind, function code from the new SR,
    width, address, data, length: a constant or a unit's: a shift's or
    a bit operation's or MULU's or DIVU's clocks).
- **Faults** override the command where the fault is found: an odd word
  address when the request is formed (the step's register, SR and PC
  changes stay, as in the model; the request and the next state become
  group 0's, the frame's words latched from the new SR and PC); BERR
  when a transaction ends (the step's effects dropped).
- **Conditions** computed from registered values before control: the 16
  condition codes, DBcc's counter at 0, CHK's comparisons, a zero
  divisor (from the data in, the extension word, or the register),
  MOVEM's next register in its mask, an interrupt pending.
- **Checks in simulation:** a unit claimed twice in one step, or a read
  port used for a register other than the one the port function chose,
  sets a flag in the command that the lockstep tests treat as a failure
  (pruned in synthesis).

## The simulation (P.5, `cpus/m68k/sim/`)

The core's Verilog (`make m68k-hdl`) in Verilator (`--prefix Vm68k`, built
by `zig c++`), behind a thin C++ shim (`vm68k.cpp`: peek the outputs with
DTACK asserted, then a rising edge), clocked by a Zig library
(`lib.zig`) whose C ABI is `m68k.h`:

- `m68k_new(read, write, user)`, `m68k_set_iack`, `m68k_set_ipl`,
  `m68k_reset` (SSP and PC from the vectors, through the callbacks; the
  counts start at the first instruction), `m68k_step` (one instruction),
  `m68k_run(limit)` (until STOP with nothing to wake it, a halt, or the
  first instruction start past the limit), `m68k_clocks`,
  `m68k_instructions`, `m68k_stopped`, `m68k_halted`, `m68k_reg(n)` (the
  top's debug port: D0-D7, A0-A7, USP, SSP, SR, PC, IR).
- No wait states: a transaction takes the chip's clocks; the callbacks
  answer it on its last clock (TAS: a read and a write).

`make m68k-sim` builds `build/m68k/sim/lib/libm68k.so` with
`include/m68k.h`, `bin/m68k-sim` (the harness: m68k-run's options and
output, on the same library code) and `bin/m68k-ctest` (`test.c`, a C
program linked against the library). **`make m68k-sim-test`, P.5's gate**
(2026-10-21, green on the worker): m68k-sim's output on the sample program
(`test/asm/sum.s`) is m68k-run's, byte for byte (1820 cycles, 203
instructions, every register); m68k-ctest gets the same counts through
the shared library. About 5 minutes from nothing (Clash 2, Verilator and
the C++ compile the rest); not in `make test` or `make ci` yet.

**Its speed was the first core's structure's** (P.4f's finding; Core3's
model runs 108,000 clocks a second, P.4h): Verilator
evaluates the whole step function every evaluation, two a clock; 44,000
clocks a second on the worker (1,000,000 clocks of `BRA *` in 22.8 s;
three evaluations a clock were 34,000), against the model's 1.3 M
instructions a second (`m68k-run`). P.4g, the core as control and
datapath, is for this too; until then the model (`M68k.Run`, `m68k-run`)
is the fast way to run a benchmark, the Verilator model the way to run
the hardware's code.
